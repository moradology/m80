# Agent-use-case roadmap (2026-05-04)

After hard look at competition (smolvm/libkrun, kata-containers, e2b SaaS),
m80's defensible niche is **self-hosted, Rust-embeddable, Firecracker-based,
agent-shaped sub-second warm pool**. The gap is real (e2b is hosted; Kata is
container-shaped; smolvm is libkrun and slower). To occupy it, m80 needs
features today the competition either fakes or doesn't have.

## Priority ranking

| # | Feature | Why for agents | Bead | Priority |
|--:|---|---|---|:-:|
| 1 | **Snapshot/restore** | Replaces 2-3 s cold boot per launch with ~125-200 ms warm restore. The single biggest agent-UX unlock. | `m80-rrp.3` (under `m80-rrp` warm-pool epic) | P1 |
| 2 | **File-ops verbs** | Agents constantly move small files in/out. Today every file op round-trips bash+base64. Smolvm has these; we don't. | `m80-6zim` (epic + 6 leaves) | P2 |
| 3 | **Real streaming exec** | Long-running output should arrive as produced, not at exit. Smolvm fakes this; we'd be the only one with it real. | `m80-5vha` (epic + 6 leaves) | P2 |
| 4 | **Persistent VM mode** | Multi-turn agents shouldn't pay even snapshot-restore between turns within one conversation. | `m80-qokt.2` (epic) | P1 |
| 5 | **Storage pivot** (RO base + overlay) | ~700 ms cold-launch saved + per-VM disk drops to O(writes). Architectural cleanup that the "intentional clone" Non-goals line was load-bearing on a wrong premise. | `m80-f2zc` (epic + 8 leaves) | P2 |

|---|---|---|

## Sequencing rationale

**Why snapshot first.** Without sub-200 ms warm restore, m80 isn't agent-grade.
Multi-turn agent loops do many short execs per conversation. 3 s cold-boot per
turn is unusable. `m80-rrp.3` was P2; promoted to P1 today.

**Why file-ops next.** Once warm starts work, the wire becomes the bottleneck.
Agents reading/writing files via bash+base64 is expensive (process spawn,
1 MiB CAPTURE_LIMIT, shell quoting). Smolvm has these verbs; we should too.

**Why streaming after file-ops.** Streaming is more architecturally invasive
(multi-frame wire) and less universally needed than file-ops. File-ops are
strictly additive (Payload variants); streaming is a new wire shape (opt-in
via `ExecRequest.streaming`).

**Why persistent VM mode in there.** A multi-turn agent in one conversation
should reuse one VM across turns. Today `RunningSandbox::exec` consumes self
(fixed in `m80-qokt.2`). Without this, even snapshot-warm starts pay the
restore tax per turn.

**Why storage pivot last.** It saves ~700 ms cold boot, but cold boot is the
rare path once snapshot is in. Architecturally still worth doing — the
"intentional clone" defense in `m80-storage` README was wrong — but not the
agent-UX unlock.
