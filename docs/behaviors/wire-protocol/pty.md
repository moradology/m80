# Wire Protocol — PTY Exec

Behavior capture for bead `m80-lt15.13`.

## Purpose

PTY exec is the interactive terminal protocol for `m80 run --tty`. It is
separate from pipe-mode `ExecRequest` so the existing stdout/stderr contract
does not drift.

Pipe streaming emits `exec_stdout`, `exec_stderr`, and `exec_exit`. PTY exec
emits a single merged terminal byte stream and terminal-specific control
frames:

- `pty_request` — host asks guestd to spawn a foreground terminal process
- `pty_input` — host terminal bytes to guest PTY
- `pty_output` — guest PTY bytes to host terminal
- `pty_resize` — host terminal-size change
- `pty_control` — host-originated EOF or wrapper signal request
- `pty_exit` — exactly one terminal result frame

Every PTY frame is wrapped in `Envelope<T>` and carries the same opaque
`request_id` for one session.

## Request

`PtyRequest` carries the same process identity as pipe exec: `program`,
`args`, optional `cwd`, optional `env`, and optional `timeout_ms`. It also
carries the initial `PtySize` with rows and columns plus optional pixel
dimensions.

`PtyRequest` has no workspace, egress, tool, credential, or agent-policy
fields. Those remain host orchestration and adapter concerns.

## Terminal Bytes

`PtyInput` and `PtyOutput` carry raw bytes as base64-encoded JSON strings.
Both have a monotonic `seq` within their direction for one request.

PTY output is the terminal stream. It does not preserve separate stdout and
stderr streams because a pseudo-terminal merges them by design.

Each frame still uses the global NDJSON size cap. A large terminal stream is
represented as many bounded `pty_output` frames, not as one aggregate output
frame. Backpressure is inherited from the transport: a slow reader should fill
the socket and block the writer rather than queueing unbounded terminal bytes.

## Resize And Control

`PtyResize` carries a `PtySize` update. Resize frames are host-to-guest and
are ordered on the same connection with input/control frames.

`PtyControl` carries host-originated terminal controls:

- `Eof` — host terminal input reached EOF
- `Signal { signal }` — wrapper asks guestd to signal the foreground
  process/session

Normal terminal-generated bytes, such as Ctrl-C from an attached terminal,
travel as `PtyInput`. `PtyControl::Signal` is for wrapper-side lifecycle
events such as shutdown, hangup, or forced cancellation.

## Terminal Frame

`PtyExit` is the only terminal result frame. It carries:

- `status: ExecStatus`
- optional `exit_code`
- optional platform `exit_signal` name
- total input and output byte counts
- `truncated`
- `ExecTiming`

After `pty_exit`, guestd must not emit another `pty_output` for the same
request. A PTY session that exits without terminal output is valid, but it
still emits exactly one `pty_exit`.
